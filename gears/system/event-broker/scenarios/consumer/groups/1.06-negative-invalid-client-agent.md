# Reject a non-ASCII or over-length text field on group create

Text fields on the broker API are printable ASCII (`0x20`-`0x7E`) and length-bounded in bytes: `client_agent` follows the RFC 9110 User-Agent grammar at 1-256 bytes, and `description` admits up to 1024 bytes. A body carrying a byte outside the printable range, or a value past its bound, is rejected with `400 BadRequest`.

The two rules report separately, because the corrective action differs: a mis-encoded value must be re-encoded, an over-long one shortened. Encoding is reported first when a value breaks both, since shortening it would not make it acceptable.

**The response body carries no part of the submitted value.** It names the field, states what the rule requires, and gives a machine-readable reason. A caller already knows what it sent, and an error body travels into logs and clients where the request was never meant to go.

## Request - a non-ASCII `description`

A `description` carrying bytes outside the printable-ASCII range (a non-ASCII multibyte character plus an embedded control byte, both rejected):

```http
POST /v1/consumer-groups HTTP/1.1
Host: broker.example.com
Authorization: Bearer <tenant-token>
Content-Type: application/json

{
  "client_agent": "example-consumer/1.0",
  "description": "<non-ASCII multibyte char and a control byte>"
}
```

## Expected response

- `400 Bad Request` (`PD`)
- Problem Details body naming the offending field and the rule it broke.

```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.invalid_argument.v1~",
  "title": "Invalid Argument",
  "status": 400,
  "detail": "Request validation failed",
  "instance": "/v1/consumer-groups",
  "trace_id": "<request-trace-id>",
  "context": {
    "field_violations": [
      {
        "field": "description",
        "description": "must contain only printable ASCII (0x20-0x7E)",
        "reason": "ascii_only"
      }
    ],
    "resource_type": "gts.cf.core.events.request.v1~"
  }
}
```

`detail` is the canonical fixed phrase for a validation failure; the per-field text belongs to `field_violations[].description`.

## Request - an over-length `client_agent`

A `client_agent` of 257 bytes, one past its bound:

```http
POST /v1/consumer-groups HTTP/1.1
Host: broker.example.com
Authorization: Bearer <tenant-token>
Content-Type: application/json

{
  "client_agent": "<257 printable-ASCII bytes>"
}
```

## Expected response

- `400 Bad Request` (`PD`)
- The length rule reports its own reason, and states the bound and the measured length. A byte count is a fact about the value rather than a reproduction of it.

```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.invalid_argument.v1~",
  "title": "Invalid Argument",
  "status": 400,
  "detail": "Request validation failed",
  "instance": "/v1/consumer-groups",
  "trace_id": "<request-trace-id>",
  "context": {
    "field_violations": [
      {
        "field": "client_agent",
        "description": "must be 1-256 bytes, got 257",
        "reason": "field_too_long"
      }
    ],
    "resource_type": "gts.cf.core.events.request.v1~"
  }
}
```

An empty `client_agent` is rejected by the same rule, since its bound starts at 1 byte. An empty `description` is accepted: the field is optional, so an empty string and an absent field agree.

## Side effects

- No group is created (`evbk_consumer_group` gains no row).
